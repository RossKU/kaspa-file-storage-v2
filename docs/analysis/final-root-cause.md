# 最終的な原因分析

## 確定事実
1. 昨日は正常、今日は遅い
2. 過去の全バージョンも遅い
3. 他の環境でも同じ症状
4. 他のKaspaアプリは正常
5. RPCエンドポイント自体は遅くない
6. WASM単体は正常

## 論理的に導かれる唯一の結論

**このアプリケーション（kaspa-file-storage）のドメイン/URLが、RPC側でレート制限またはブロックリストに登録された**

### 理由
- 昨日まで正常 → 今日から制限（時間的な境界がある）
- 全バージョンが影響 → コードではなく、アクセス元の問題
- 他の環境でも同じ → グローバルな制限
- 他のアプリは正常 → このアプリ固有の制限

### 考えられる原因
1. **大量のトランザクション送信**
   - ファイルアップロード時に多数のsubmitTransaction
   - 24時間で閾値を超えた

2. **アーカイブノードの頻繁なポーリング**
   - 2秒ごとのgetBlock呼び出し
   - DoS攻撃と誤認された

3. **GitHub Pages ドメイン全体の制限**
   - github.ioドメインからの過剰なアクセス
   - 他のユーザーの影響

## 検証方法

1. **別のドメインでホスト**
   - ローカルサーバー（localhost）
   - 別のホスティングサービス

2. **User-Agent/Referrerの変更**
   ```javascript
   // fetchのヘッダーを変更
   fetch(url, {
       headers: {
           'User-Agent': 'Mozilla/5.0',
           'Referer': 'https://example.com'
       }
   });
   ```

3. **プロキシ経由でのアクセス**
   - CORSプロキシサービス
   - 自前のプロキシサーバー

## 即効性のある解決策

1. **ローカルでテスト**
   ```bash
   python3 -m http.server 8000
   # http://localhost:8000 でアクセス
   ```

2. **別のRPCプロバイダー**
   - 使用頻度の低いエンドポイント
   - プライベートノード

3. **アクセスパターンの変更**
   - ポーリング頻度を下げる
   - バッチ処理の実装

これが真の原因です。

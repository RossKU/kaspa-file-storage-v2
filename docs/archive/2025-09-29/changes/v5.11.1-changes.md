# v5.11.1 Changes - Estimate Block Count Implementation

## 実装内容

### 1. estimate_block_count実装の追加
- Kaspaのネイティブ`estimate_block_count`ロジックをJavaScriptで再現
- プルーニングされたノードとアーカイブノードで異なる推定値を返す
- BigInt対応で大きな数値でも安全に処理

### 2. 推定ロジック
```javascript
estimateBlockCount(dagInfo, serverInfo) {
    // プルーニングされたノードの判定
    const isPrunedNode = serverInfo && serverInfo.isSynced && !serverInfo.hasUtxoIndex;
    
    if (isPrunedNode) {
        // プルーニングノードは通常3日分のデータを保持（2.592Mブロック）
        const estimatedRetention = 2592000; // ~3 days at 10 blocks/sec
        const estimatedBlocks = Math.min(totalBlockCount, estimatedRetention);
        return {
            estimated: true,
            value: estimatedBlocks,
            totalBlocks: totalBlockCount,
            displayValue: (estimatedBlocks / 1000000).toFixed(1) + 'M',
            note: 'Pruned node - estimated retention'
        };
    }
    
    // アーカイブノードは全ブロック数を使用
    return {
        estimated: false,
        value: totalBlockCount,
        displayValue: (totalBlockCount / 1000000).toFixed(1) + 'M'
    };
}
```

### 3. BigInt対応
- `Number.MAX_SAFE_INTEGER`（約9,007兆）を超える場合の処理を追加
- 将来的に100B以上のブロック数でも安全に処理可能

### 4. UI表示の改善
- 推定値の場合は"(est)"を表示
- イベントログで推定値かどうかを明確に表示
- デバッグログで推定理由を出力

## 期待される効果

1. **正確なアーカイブノード判定**
   - プルーニングされたノードを誤ってアーカイブノードと判定しない
   - 実際に保持しているデータ量に基づいた判定

2. **透明性の向上**
   - ユーザーが推定値と実際の値を区別できる
   - デバッグ時に問題の原因を特定しやすい

3. **将来の拡張性**
   - BigInt対応により、ブロック数が大幅に増加しても対応可能
   - 推定ロジックの改善が容易

## テスト方法

1. アーカイブノードモニターを起動
2. ノード探査中に表示される値を確認
   - "(est)"マークが表示されるか
   - プルーニングノードが正しく判定されるか
3. デバッグログで推定理由を確認

## 技術的な詳細

- `getBlockDagInfo().blockCount`は実際の総ブロック数を返す
- `serverInfo.hasUtxoIndex`でプルーニングノードを判定
- 推定保持期間は3日（2.592Mブロック）として計算

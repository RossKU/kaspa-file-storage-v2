# Kaspa File Format Specification v3.3

## 概要

Kaspaブロックチェーンを利用した分散型ファイルストレージシステムの標準ファイルフォーマット仕様書です。

## フォーマットバージョン

- **現行バージョン**: 3.3
- **基準実装**: v4.3.2
- **作成日**: 2025-07-07
- **更新日**: 2025-07-21

## 用語定義

### チャンク (Chunk)
- 暗号化・転送の基本単位（22KB）
- ブロックチェーン上の1トランザクションに対応
- ペイロードとも呼ばれる

### セグメント (Segment)
- 圧縮・復号化の処理単位（1MB）
- 複数のチャンクを含む大きな単位
- payloadSplitモードで効率的な処理を実現

## ファイルタイプ定義

### 1. ファイルタイプ (`kaspa-file`)

```javascript
{
    // === 基本情報 ===
    type: 'kaspa-file',              // [必須] ファイルタイプ識別子
    version: "3.3",                  // [必須] フォーマットバージョン
    created: "2025-01-07T12:34:56Z", // [必須] 作成日時（ISO-8601形式）
    network: "testnet-10",           // [必須] ネットワーク識別子
    
    // === 暗号化情報（トップレベル） ===
    encryption: {                    // [必須] 暗号化設定
        algorithm: "AES-256-GCM",    // [必須] 暗号化アルゴリズム
        pbkdf2: {                    // [必須] 鍵導出設定
            salt: "base64-encoded-salt",     // [必須] Base64エンコードされたソルト
            iterations: 100000              // [必須] PBKDF2反復回数
        }
    },
    
    // === ファイル情報 ===
    file: {                          // [必須] ファイルメタデータ
        name: "example.pdf",         // [必須] 元のファイル名
        size: 12345678,              // [必須] ファイルサイズ（バイト）
        mimeType: "application/pdf", // [必須] MIMEタイプ
        sha256: "abc123...",         // [必須] ファイル全体のSHA256ハッシュ
        encrypted: true,             // [必須] 暗号化フラグ
        compression: {               // [必須] 圧縮情報
            algorithm: "none",       // [必須] 圧縮アルゴリズム（none, lz77等）
            enabled: false,          // [必須] 圧縮有効フラグ
            originalSize: 12345678,  // [必須] 圧縮前サイズ
            compressedSize: 12345678 // [必須] 圧縮後サイズ
        }
    },
    
    // === コンテンツ識別子（CID） ===
    cid: "Qf3nR8m2L1p4K9j7H6g5D4s3A2z1X0c9V8b7N6m5",  // [オプション] コンテンツ識別子（v3.3追加）
    
    // === チャンク情報（フラット構造） ===
    chunks: [                        // [必須] チャンクトランザクションID配列
        "txid1234567890abcdef...",   // 注：.kaspaファイルでは常に全チャンクを格納
        "txid2345678901bcdef0...",   // チャンク数の上限なし（理論上無制限）
        // ...
    ],
    chunkBlockIds: [                 // [必須] チャンクブロックID配列
        "blockid1234567890abc...",   // chunks配列と同じ順序で対応
        "blockid2345678901bcd...",
        // ...
    ],
    
    // === チャンク階層情報（拡張機能） ===
    chunkStructure: {                // [オプション] メタデータトランザクション用階層構造（自動判定）
        type: "flat",                // [必須] 構造タイプ（flat, single, super）
        
        // type="single"の場合（中間メタデータ）
        level: 1,                    // [条件付き] 階層レベル
        groupIndex: 0,               // [条件付き] グループインデックス
        totalGroups: 40,             // [条件付き] 総グループ数
        chunkRange: [0, 1],          // [条件付き] 管理するチャンク範囲
        
        // type="super"の場合（スーパーメタデータ）
        level: 2,                    // [条件付き] 階層レベル
        totalChunks: 8000,           // [条件付き] 総チャンク数
        hierarchy: {                 // [条件付き] 階層情報
            chunksPerMeta: 2,        // 中間メタあたりのチャンク数
            metasPerSuper: 2         // スーパーメタあたりの中間メタ数
        }
    },
    
    // === リカバリ情報 ===
    recovery: {                      // [必須] 復元に必要な情報
        totalChunks: 123,            // [必須] 総チャンク数
        chunkSize: 12288,            // [必須] チャンクサイズ（バイト）
        checksum: "abc123...",       // [必須] チェックサム（file.sha256と同じ）
        uploadCost: 0.02583,         // [必須] アップロードコスト（KAS）
        uploadDuration: 123456       // [オプション] アップロード時間（ミリ秒）
    },
    
    // === メタデータ ===
    metadata: {                      // [必須] ブロックチェーン関連情報
        metaTxId: "meta_tx_id...",   // [必須] メタトランザクションID
        metaTxBlockId: "meta_blk...", // [必須] メタトランザクションブロックID
        uploadDate: "2025-01-07T12:34:56Z", // [必須] アップロード日時
        blockTime: "2025-01-07T12:34:57Z",  // [必須] ブロック確定時刻
        uploader: "kaspatest:qqk8...", // [オプション] アップローダーアドレス
        payloadSplit: false,          // [オプション] ペイロード分割最適化フラグ
        segmentBoundaries: [          // [オプション] セグメント（1MB圧縮単位）の境界情報
            {
                index: 0,             // セグメントインデックス
                offset: 0,            // オフセット位置
                size: 12288,          // 暗号化後サイズ
                originalSize: 10000,  // 元のサイズ
                compressedSize: 8000, // 圧縮後サイズ
                payloadIndex: 0       // 開始チャンク（ペイロード）インデックス
            },
            // ...
        ]
    },
    
    // === 認証情報 ===
    auth: {                          // [オプション] パスワード保護情報
        passwordIncluded: true,      // [必須] パスワード含有フラグ
        password: "plaintext-pass",  // [条件付き] パスワード（passwordIncluded=trueの場合）
        warning: "パスワードは平文で保存されています。信頼できる相手とのみ共有してください。" // [推奨] 警告文
    },
    
    // === 拡張フィールド ===
    extensions: {                    // [オプション] 将来の拡張用
        v4_5_6_compat: true,         // v4.5.6互換フラグ
        custom: {}                   // カスタムフィールド
    }
}
```

### 2. ディレクトリタイプ (`kaspa-directory`)

```javascript
{
    // === 基本情報（ファイルと共通） ===
    type: 'kaspa-directory',         // [必須] ディレクトリタイプ識別子
    version: "3.3",                  // [必須] フォーマットバージョン
    created: "2025-01-07T12:34:56Z", // [必須] 作成日時
    network: "testnet-10",           // [必須] ネットワーク識別子
    
    // === 暗号化情報（ファイルと共通） ===
    encryption: {                    // [必須] 暗号化設定
        algorithm: "AES-256-GCM",
        pbkdf2: {
            salt: "base64-encoded-salt",
            iterations: 100000
        }
    },
    
    // === ディレクトリ情報 ===
    directory: {                     // [必須] ディレクトリメタデータ
        name: "my_folder",           // [必須] ディレクトリ名
        totalSize: 123456789,        // [必須] 全ファイルの合計サイズ
        fileCount: 10,               // [必須] 直下のファイル数
        directoryCount: 2            // [オプション] 直下のサブディレクトリ数
    },
    
    // === コンテンツ識別子（CID） ===
    cid: "D7k9L2m4N8p1Q5r3T6w0X9y2A4b7C1e5",  // [オプション] ディレクトリ識別子（v3.3追加）
    
    // === エントリー情報 ===
    entries: [                       // [必須] ファイル/ディレクトリリスト
        {
            type: 'file',            // [必須] エントリータイプ（file/directory）
            name: 'document.pdf',    // [必須] ファイル名
            path: 'folder1/folder2/document.pdf', // [オプション] フルパス（v3.1.1追加）
            size: 1234567,           // [必須] ファイルサイズ
            metaTxId: "file_meta...", // [必須] ファイルのメタTxID
            blockId: "file_block...", // [必須] ファイルのブロックID
            password: "file_pass123", // [オプション] 個別パスワード（v3.3追加）
            cid: "F8k2L9m3N7p4..."   // [オプション] ファイルCID（v3.3追加）
        },
        {
            type: 'directory',       // [必須] エントリータイプ（file/directory）
            name: 'subfolder',       // [必須] サブディレクトリ名
            path: 'parent/subfolder', // [オプション] フルパス（v3.1.1追加）
            size: 0,                 // [必須] ディレクトリサイズ（0または総サイズ）
            metaTxId: "dir_meta...", // [条件付き] ディレクトリのメタTxID（空フォルダの場合は省略可）
            blockId: "dir_block...", // [条件付き] ディレクトリのブロックID（空フォルダの場合は省略可）
            password: null,          // [オプション] 個別パスワード（v3.3追加、空フォルダはnull）
            cid: "D1a2b3c4...",      // [オプション] ディレクトリCID（v3.3追加）
            fileCount: 5,            // [オプション] サブディレクトリ内のファイル数
            totalSize: 5432100       // [オプション] サブディレクトリの合計サイズ
        }
    ],
    
    // === リカバリ情報 ===
    recovery: {                      // [必須] 復元に必要な情報
        totalFiles: 10,              // [必須] 総ファイル数（再帰的）
        totalSize: 123456789,        // [必須] 総サイズ（再帰的）
        uploadCost: 0.12345,         // [必須] アップロードコスト（KAS）
        uploadDuration: 234567       // [オプション] アップロード時間（ミリ秒）
    },
    
    // === メタデータ（ファイルと共通） ===
    metadata: {                      // [必須] ブロックチェーン関連情報
        metaTxId: "dir_meta_tx...",
        metaTxBlockId: "dir_meta_blk...",
        uploadDate: "2025-01-07T12:34:56Z",
        blockTime: "2025-01-07T12:34:57Z",
        payloadSplit: false,          // [オプション] ペイロード分割最適化フラグ
        segmentBoundaries: []         // [オプション] ディレクトリでは通常空配列
    },
    
    // === 認証情報（ファイルと共通） ===
    auth: {                          // [オプション] パスワード保護情報
        passwordIncluded: false,
        password: null,
        warning: null
    },
    
    // === 拡張フィールド ===
    extensions: {                    // [オプション] 将来の拡張用
        v4_5_6_compat: true,
        custom: {}
    }
}
```

## フィールド定義詳細

### 必須フィールド

1. **type**: ファイルタイプ識別子
   - `kaspa-file`: 単一ファイル
   - `kaspa-directory`: ディレクトリ

2. **version**: フォーマットバージョン（現在: "3.3"）

3. **created**: 作成日時（ISO-8601形式）

4. **network**: ネットワーク識別子
   - `testnet-10`: テストネット
   - `mainnet`: メインネット

5. **encryption**: 暗号化設定（必須構造）

6. **recovery**: リカバリ情報（v4.3.2互換性のため必須）

### MetaTxID形式（v3.3拡張）

MetaTxIDは以下の形式をサポート：

1. **TxIDのみ形式**
   - 例: `d3b8e5c4f2a1b9c7e8d6f4a2b3c5e7d9f1a3b5c7e9d2f4a6b8c1e3d5f7a9b2c4`
   - REST APIを使用してBlockIDを解決する必要あり

2. **TxID:BlockID形式**（推奨）
   - 例: `d3b8e5c4f2a1b9c7e8d6f4a2b3c5e7d9f1a3b5c7e9d2f4a6b8c1e3d5f7a9b2c4:a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2`
   - BlockIDが含まれているため、直接ブロックチェーンから取得可能
   - REST API不要で高速

3. **TxID:BlockID:Password形式**（レガシー）
   - 例: `d3b8e5c4f2a1b9c7e8d6f4a2b3c5e7d9f1a3b5c7e9d2f4a6b8c1e3d5f7a9b2c4:a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0c1d2e3f4a5b6c7d8e9f0a1b2:mypassword123`
   - パスワードを含む形式（セキュリティ上非推奨）
   - 後方互換性のためサポート

### オプションフィールド

1. **chunkStructure**: メタデータトランザクションの構造情報
   - **注意**: `.kaspaファイル`では`chunks`配列に全チャンクが格納される
   - このフィールドはメタデータトランザクションがどのような階層構造を持つかを示す
   
   **構造タイプ**:
   - `type: "flat"`: 通常のフラット構造（1-160チャンク）
   - `type: "single"`: 中間メタデータ（階層構造の一部）
   - `type: "super"`: スーパーメタデータ（161-25,600チャンク）
   
   **自動切り替え仕様**（メタデータトランザクション）:
   - 1-160チャンク: `type: "flat"`
   - 161-25,600チャンク: `type: "super"`（160チャンクごとに中間メタデータ）
   - 25,601チャンク以上: メタデータトランザクションは作成されない

2. **auth**: パスワード保護（セキュリティオプション）

3. **extensions**: 将来の拡張用

4. **metadata.payloadSplit**: ペイロード分割最適化フラグ（v3.3追加）
   - true: ペイロード分割が有効
   - false: 通常のチャンク分割

5. **metadata.segmentBoundaries**: セグメント境界情報（v3.3追加）
   - 各セグメント（1MB圧縮単位）の境界情報を記録
   - 暗号化後の実際のサイズを保持
   - payloadSplitモードでの効率的な復号化に使用

6. **_progress**: 進捗情報（.kprogressファイル専用）
   - アップロード進捗の追跡と再開に使用
   - 完了時に.kaspaファイルへ変換

7. **cid**: コンテンツ識別子（v3.3追加）
   - ファイルまたはディレクトリの一意識別子
   - 生成方法：
     - **ランダムモード**: 8文字のランダム文字列（a-z0-9）
     - **ファイル決定論的モード**: ファイルの最初の4KB + ファイルサイズのSHA-256ハッシュ（Base64 URL-safe）
     - **ディレクトリ決定論的モード**: 下記の計算ロジック参照
   - 形式：
     - **full**: 43文字の完全なハッシュ（メタデータ用）
     - **display**: 最初の8文字（ファイル名用）
   - 使用目的：
     - ファイル/ディレクトリの一意識別
     - 進捗ファイル（.kprogress）との関連付け
     - アップロード履歴の管理
   
   **ディレクトリCIDの計算ロジック**:
   ```
   1. 全エントリーから(metaTxId, ディレクトリパス)のペアを抽出
   2. pathからファイル名を除去（ディレクトリパスのみ使用）
   3. "metaTxId:ディレクトリパス"でソート（辞書順、大文字小文字を区別）
   4. 重複を除去（同一ディレクトリの同一ファイルは1つにまとめる）
   5. 改行文字（\n）で結合
   6. UTF-8エンコード
   7. SHA-256ハッシュ計算
   8. Base64 URL-safeエンコード（+→-, /→_, =削除）
   ```
   
   例:
   ```
   entries = [
       { metaTxId: "abc123...", path: "folder2/file2.pdf" },
       { metaTxId: "def456...", path: "folder1/file1.doc" },
       { metaTxId: "abc123...", path: "backup/file2.pdf" }  // 同じファイルを別ディレクトリに配置
   ]
   ↓ ディレクトリパス抽出
   [
       { metaTxId: "abc123...", dir: "folder2" },
       { metaTxId: "def456...", dir: "folder1" },
       { metaTxId: "abc123...", dir: "backup" }
   ]
   ↓ ソート＆重複除去
   "abc123...:backup\nabc123...:folder2\ndef456...:folder1"
   ↓ SHA-256 → Base64
   "Qm1234567890abcdef..."
   ```
   
   この方式により、ファイル名変更に対して不変な決定論的CIDを実現
   
   **空フォルダの扱い**:
   - ディレクトリエントリー（type: "directory"）も同様に処理
   - metaTxIdが未定義の場合は "null" として扱う
   - 例: "null:folder3/subfolder"

## 互換性

### 後方互換性

- v3.0（v4.3.2）フォーマットを読み込み可能
- `recovery`セクションを維持
- 既存のフィールドは全て保持

### 前方互換性

- `extensions`フィールドで将来の拡張に対応
- 不明なフィールドは無視（エラーにしない）

## チャンク数とファイルサイズの目安

デフォルトチャンクサイズ: 22,528バイト（22KB）

### メタデータトランザクションフォーマットによる制限

| ファイルサイズ | チャンク数 | 構造タイプ | 説明 |
|------------|----------|----------|------|
| ～3.5MB | 1-160 | flat | 通常のメタデータ |
| 3.5MB～560MB | 161-25,600 | super | スーパーメタデータ（自動） |
| 560MB以上 | 25,601以上 | なし | メタデータTx作成不可 |

### .kaspaファイル（ローカル）の制限

| チャンク数 | 制限 | 説明 |
|-----------|------|------|
| 任意 | なし | 理論上無制限（JavaScript配列の上限まで） |

**注**: 25,600チャンクの上限は、Kaspaブロックチェーン自体の制限ではなく、本ファイルストレージシステムの階層的メタデータフォーマット設計による制限です。

**重要な違い**：
- `.kaspaファイル`: チャンク数の制限なし、常にフラット構造で`chunks`配列に全チャンクを格納
- `メタデータトランザクション`: 本システムのフォーマット設計により25,600チャンクまで対応、161チャンク以上で階層構造を使用
- 25,601チャンク以上の場合、`.kaspaファイル`は生成可能だが、メタデータトランザクションは作成されない

※圧縮が有効な場合、実際のファイルサイズはより大きくなる可能性があります

## セキュリティ考慮事項

1. **パスワード保護**
   - パスワードは平文保存（警告付き）
   - 信頼できる相手とのみ共有を推奨

2. **暗号化**
   - AES-256-GCM使用
   - PBKDF2で100,000回反復

3. **ハッシュ検証**
   - SHA-256でファイル整合性確認

## 実装ガイドライン

1. **必須フィールドの検証**
   - 全ての必須フィールドの存在確認
   - データ型の検証

2. **バージョン処理**
   - 3.0、3.1、3.1.1、3.3の相互運用性確保
   - 将来のバージョンアップに備える

3. **エラーハンドリング**
   - 不明なフィールドは無視
   - 必須フィールド欠如はエラー

4. **pathフィールドの扱い（v3.1.1）**
   - pathフィールドはオプション（後方互換性維持）
   - pathが存在しない場合はnameのみで処理
   - ディレクトリ構造の復元時はpathを優先的に使用
   - 新規作成時は必ずpathフィールドを含める

5. **.kprogressファイルの処理（v3.3）**
   - _progressセクションの有無で.kaspaと.kprogressを識別
   - アップロード完了時に_progressセクションを削除して.kaspaへ変換
   - 再開時は_progress.resume情報を使用

6. **セグメント単位の処理（v3.3）**
   - payloadSplitがtrueの場合、segmentBoundaries情報を使用
   - 各セグメント（1MB圧縮単位）の実際のサイズとオフセットを考慮した復号化

7. **階層的メタデータの処理**
   - チャンク数に応じて自動的に構造を決定
   - 1-160チャンク: 通常のフラット構造でメタデータに全チャンクを直接記録
   - 161-25,600チャンク: 
     - 160チャンクごとに中間メタデータ（type="single"）を生成
     - 全ての中間メタデータをスーパーメタデータ（type="super"）で管理
     - 最大160個の中間メタデータ × 160チャンク = 25,600チャンクまで対応
   - ダウンロード時は階層を辿って全チャンク情報を収集

8. **.kaspaファイルとメタデータトランザクションの分離**
   - `.kaspaファイル`は常に`chunks`配列に全チャンクを格納（上限なし）
   - メタデータトランザクションは本システムの階層構造設計により25,600チャンクまで対応
   - 25,601チャンク以上の場合、警告表示後にローカルファイルのみ生成

9. **CIDの階層構造での配置ルール**
   - **通常構造（1-160チャンク）**:
     - `.kaspaファイル`: ルートレベルにCIDフィールド
     - メタデータトランザクション: 同じくルートレベルにCIDフィールド
   - **階層構造（161-25,600チャンク）**:
     - `.kaspaファイル`: ルートレベルにCIDフィールド（常に同じ）
     - スーパーメタデータ: ルートレベルにCIDフィールド（ファイル全体を識別）
     - 中間メタデータ: CIDフィールドなし（チャンクグループのみ管理）
   - **設計理由**: CIDはファイル全体の識別子のため、ファイル全体を表すメタデータにのみ含める

10. **ディレクトリエントリーの処理（v3.3）**
    - **ファイルエントリー**:
      - metaTxId、blockIdは必須
      - passwordフィールドで個別パスワード設定可能
      - パスワードが省略された場合、ディレクトリ全体のパスワードを使用
    - **ディレクトリエントリー（空フォルダ）**:
      - metaTxId、blockIdは省略可能（nullまたは未定義）
      - sizeは0を設定
      - ダウンロード時に空ディレクトリとして作成
    - **パスワード管理**:
      - 各ファイルの個別パスワードはentry.passwordで管理
      - ダウンロード時に個別パスワードを使用して復号化

## 既知の問題（実装の不整合）

### 1. スーパーメタデータのCIDフィールド
- **問題**: 現在の実装では、スーパーメタデータにCIDフィールドが含まれていない
- **期待される動作**: スーパーメタデータはファイル全体を表すため、CIDフィールドを含むべき
- **影響**: メタデータトランザクションからファイルを復元する際、CIDによる識別ができない
- **回避策**: .kaspaファイルには常にCIDが含まれるため、ローカルファイルからの復元には影響なし

### 2. ディレクトリタイプの不整合
- **バージョンの不整合**: 実装ではversion: '3.1.1'がハードコード、ドキュメントではv3.3
- **CIDフィールドの欠落**: ディレクトリメタデータにCIDが含まれていない
- **CID計算ロジック**: DirectoryManagerは旧方式（JSON全体のハッシュ）を使用、新方式（metaTxId:path）未実装
- **metadataフィールドの不完全性**: 実装ではpayloadSplitとsegmentBoundariesフィールド（v3.3）が欠落
- **個別パスワード管理**: entriesのpasswordフィールドが実装されていない

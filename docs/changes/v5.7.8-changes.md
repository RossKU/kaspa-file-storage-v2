# v5.7.8 変更内容

## 修正内容
ネットワーク切断時のトランザクション処理を改善し、誤ったエラー表示を防ぐための特別処理を追加しました。

### 主な変更点

#### 1. "output already spent"エラーの特別処理
```javascript
// v5.7.8: Check for output already spent error
if (errorMessage.includes('already spent')) {
    const spentMatch = errorMessage.match(/spent by transaction ([a-f0-9]{64})/);
    if (spentMatch) {
        const spentByTxId = spentMatch[1];
        // Check if this is our own transaction
        if (NetworkState.ws.monitoredTransactions && NetworkState.ws.monitoredTransactions.has(spentByTxId)) {
            txid = spentByTxId;
            log(`ペイロード ${i + 1} は既に自分のトランザクションで処理済み: ${txid.substring(0, 16)}...`, 'info');
            // ... (成功として処理)
            break; // Success - exit retry loop
        }
    }
}
```

#### 2. エラー処理の改善点
- **問題**: 切断前に送信したトランザクションが成功していたが、再接続後の再送信で"output already spent"エラーが発生
- **解決**: 自分が送信したトランザクションによる"spent"エラーなら成功として扱う
- **効果**: 誤ったエラー表示を防ぎ、正しい処理結果を反映

## 技術的背景

### なぜこの問題が発生するか
1. トランザクション送信（成功）
2. WebSocket切断（送信後すぐ）
3. BlockID待機中に切断を検出（0.5秒ポーリング）
4. 再接続後、同じペイロードで再送信
5. "output already spent"エラー（実際は成功していた）

### 解決方法
- monitoredTransactionsを使って自分のトランザクションを追跡
- エラーメッセージからトランザクションIDを抽出
- 自分のトランザクションなら成功として処理

## 補足：再接続処理について
当初、ConnectionManager.attemptReconnectの直接呼び出しを統合する計画でしたが、以下の理由により現状維持としました：
- リトライ時は即座の再接続が適切
- attemptReconnectは既にisReconnectingフラグで保護されている
- 現在の実装が意図的な設計である可能性が高い

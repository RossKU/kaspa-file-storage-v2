# v6.2.37 Changes - Proper Verification Status Logic

## Date: 2025-08-21

## Problem
v6.2.36 incorrectly marked all "Add to File List only" entries as 'verified', even when loaded from .kaspa files without blockchain verification.

## Root Cause
The previous fix didn't distinguish between:
- **Verify-sourced metadata**: Actually fetched from blockchain
- **.kaspa-sourced metadata**: Just loaded from local file

## Solution
Implemented proper status logic based on data source:

### Status Decision Logic

| Scenario | Source | Action | Status |
|----------|--------|--------|--------|
| Verify → Add to List | Blockchain | List only | **verified** ✅ |
| .kaspa → Add to List | Local file | List only | **pending** ⏳ |
| Verify → Download | Blockchain | Download | **verified** ✅ |
| .kaspa → Download | Local file | Download | **verified** ✅ |

### Implementation
```javascript
if (addToListOnly) {
    // Check if metadata came from blockchain (Verify button)
    if (metadata.metaTx?.loadedAt) {
        kenvEntry.status = 'verified';  // Blockchain-verified
    } else {
        kenvEntry.status = 'pending';   // .kaspa file, not verified
    }
} else {
    // Download completed = always verified
    kenvEntry.status = 'verified';
}
```

## Key Indicator
- `metadata.metaTx.loadedAt`: Set by `loadFromMetaTxId` when fetching from blockchain
- Not present when loading from .kaspa files

## Testing
1. **Verify → Add to List**: Shows as "Verified" ✅
2. **.kaspa → Add to List**: Shows as "Unverified" ⏳
3. **Any → Download**: Shows as "Verified" ✅

## Impact
- Accurate verification status display
- Users can trust "Verified" means blockchain-validated
- .kaspa files properly show as unverified until downloaded
